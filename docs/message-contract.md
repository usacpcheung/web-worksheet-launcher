# Message Contract (Phase 1)

This document defines the launch contract and postMessage contract between:

- **Parent app** (`parent_prototype/parent.html`)
- **Popup renderer** (`server/worksheet_launcher/render.html`)

## 1) Launch URL contract

The popup URL **must** follow:

`?launchId=<opaque-id>`

Where:

- `launchId`: opaque identifier generated by the parent/backend launch service.
  It MUST be treated as an opaque token by the popup renderer (no client-side
  schema assumptions).

Example shape:

`https://<host>/worksheet/render.html?launchId=<opaque-id>`

Migration note (hash → query):

Hash-fragment launch data is not reliable through OIDC redirects because
intermediate identity/redirect flows may drop, overwrite, or fail to preserve
fragment state. The contract therefore uses a query parameter launch handle
(`launchId`) instead of hash payload transport.

## 2) Launch lifecycle

Launches are tracked server-side (or in another trusted authority) by
`launchId`.

### 2.1 Create launch

Before opening the popup, parent creates a launch record and receives
`launchId`. The launch record stores the authoritative launch context needed by
the renderer and result validation flow (for example: worksheet payload,
request id `rid`, trusted parent origin, tenant/client/user context, creation timestamp, TTL).

### 2.1.1 Required launch record fields

Each launch record must persist all of the following fields:

- `launchId` (high-entropy random opaque id)
- `rid`
- `worksheet` (JSON payload)
- `returnOrigin` (normalized URL origin)
- `tenantId`, `clientId`, `createdBy`
- `createdAt`, `expiresAt`, `consumedAt`

### 2.2 Consume launch

When renderer loads with `?launchId=...`, it resolves launch context from the
trusted launch store. A launch is considered consumed once a valid completion is
accepted/applied by parent for its corresponding `rid`.

### 2.3 Expiry behavior

Launches MUST expire after a configured TTL. If a launch is missing, expired, or
otherwise invalid at resolution time, renderer must fail closed (show error, do
not proceed with normal send flow). Backend storage must include cleanup (for example,
TTL index in DB/Redis or periodic cleanup job for in-memory stores) so expired
records are eventually removed.

### 2.4 One-time / replay behavior

Launches are single-use. Once consumed, any further attempts to use the same
`launchId` (or replay a result for the same `rid`) MUST be rejected and have no
effect.


## 3) Launch API contract (backend serving renderer)

The backend that serves `server/worksheet_launcher/render.html` also provides launch APIs.

### 3.1 `POST /api/launches`

Purpose: create a launch record and return a one-time launch handle.

Request body:

```json
{
  "rid": "request-id",
  "worksheet": { "v": 1, "title": "...", "q": ["..."], "rewrite": true },
  "returnOrigin": "https://parent.example"
}
```

Validation requirements:

- `rid` is a non-empty string.
- `worksheet` satisfies the worksheet payload schema in this document.
- `returnOrigin` is an absolute `http(s)` URL; backend stores and returns normalized `.origin`.
- Auth context provides `tenantId`, `clientId`, and `createdBy` (for example via trusted headers/session) so they are written into the launch record.
- `returnOrigin` must match a server-side integration allowlist.
- Renderer session identity (for example `x-renderer-session-id`) is required and bound to launch creation for consume-time verification.
- Create endpoint should be rate-limited per client/IP.

Success response (`201`):

```json
{ "launchId": "opaque-id", "expiresAt": "ISO-8601" }
```

### 3.2 `POST /api/launches/consume` or `GET /api/launches/:launchId`

Purpose: resolve and consume one launch.

Validation and enforcement requirements:

- `launchId` format is validated.
- authn/authz is enforced before returning launch data.
- consume requires authenticated renderer session and must verify the same bound renderer session from create time.
- consume should be rate-limited per client/IP.
- launch is rejected if missing, expired, or already consumed.
- expiry check is strict: reject when `now > expiresAt`.
- consume operation must be atomic (`consumedAt` can transition from `null` to timestamp only once).

Success response (`200`):

```json
{
  "rid": "request-id",
  "worksheet": { "v": 1, "title": "...", "q": ["..."] },
  "returnOrigin": "https://parent.example"
}
```

### 3.3 Structured error responses

Launch API errors must return structured `{ error: { code, message } }` payloads.
Required error codes:

- `unauthorized`
- `invalid_payload`
- `not_found`
- `expired`
- `already_consumed`
- `origin_not_allowed`
- `rate_limited`
- `already_exists`
- `already_revoked`

### 3.4 Security logging requirements

Security-sensitive events should be logged, including:

- invalid authentication attempts
- replay consume attempts
- return-origin allowlist mismatches

Logs must avoid storing full worksheet question text (`worksheet.q` content) and should only include minimal identifiers/metadata.

## 4) Integration onboarding contract

### 4.1 Register integration

`POST /api/integrations/register`

Registers external parent integration metadata and provisions initial credentials.

Request body:

```json
{
  "tenantId": "tenant-1",
  "clientId": "client-1",
  "allowedReturnOrigins": ["https://parent.example"],
  "ownerMetadata": { "ownerTeam": "learning-platform", "contact": "owner@example.com" }
}
```

Success response includes onboarding outputs for integrators:

- `apiBaseUrl`
- `authMethod`
- `tenantId`
- `clientId`
- initial credential material (`credentialId`, `clientSecret`)

### 4.2 Credential lifecycle

- `POST /api/integrations/credentials/rotate` rotates credentials by creating a new active credential and deactivating prior active credentials.
- `POST /api/integrations/credentials/revoke` revokes a specific credential.
- `GET /api/integrations/:tenantId/:clientId/onboarding` returns current integrator onboarding metadata (without secret material).

### 4.3 Audit records

- Registration and credential lifecycle changes are recorded in an audit trail.
- `GET /api/integrations/audit` exposes audit records (admin-authenticated) with optional tenant/client filters.

## 5) Worksheet payload schema

```json
{ "v": 1, "title": "string", "q": ["...1-N"], "rewrite": true }
```

Validation rules:

- `v` must equal `1`
- `title` should be a string when present
- `q` must be an array of strings with length `1..N` (`N >= 1`)
- `rewrite` should be a boolean when present

## 6) Popup → parent message schema

```json
{
  "type": "worksheetResult",
  "rid": "...",
  "worksheet": { "v": 1, "title": "...", "q": ["..."] },
  "answers": [
    { "index": 0, "question": "...", "answer": "...", "raw": "...", "rewritten": "..." }
  ],
  "meta": { "sentAt": "ISO-8601" }
}
```

Notes:

- `type` is fixed to `worksheetResult`
- `rid` must echo the launch `rid`
- `answers[index]` and `answers[].index` must both map to the same question order as `worksheet.q`
- `answer` is the canonical value for each question; `raw` and `rewritten` are echoed for compatibility with existing parent mapping logic
- `meta.sentAt` is an ISO-8601 timestamp string

## 7) Parent validation requirements

On `message` events, parent must reject payloads unless all mandatory checks pass.

Mandatory:

1. `event.origin` exactly matches the trusted renderer origin
2. `event.data.type === "worksheetResult"`
3. `event.data.rid` equals the outstanding request id (`rid`) used to launch popup

Recommended hardening:

4. `event.source === popupRef` (same popup window reference returned by `window.open(...)`)

If any mandatory check fails, ignore message and do not apply results.

## 8) One-shot / anti-replay expectation

After parent accepts and applies one valid `worksheetResult` for a launch `rid`, that launch
context must be treated as consumed. Parent should clear (or mark consumed) the outstanding
launch context so any subsequent message for that `rid` is rejected and has no effect.

## 9) Phase boundary

Phase 1 only defines contracts/scaffolding.
No new runtime behavior is introduced by this document.
